# Universal Developer Portfolio Infographic Prompt

> Create a polished **16:9 developer portfolio infographic image** for the application described below.
>
> The image should communicate three things immediately:
>
> **1. What the product does**
> **2. How the system works**
> **3. What technologies power it**
>
> Design it as a professional **product + engineering portfolio image**, not as a marketing poster or detailed system-design document.
>

> # VISUAL STYLE
>
> Use a **minimal modern developer-tool / SaaS aesthetic**.
>
> * White or very light neutral background
> * Dark navy primary typography
> * Muted pastel blue and green section backgrounds
> * Purple only as a secondary accent where useful
> * Thin borders
> * Subtle or no shadows
> * Consistent rounded cards
> * Simple flat technical icons
> * Clean arrows showing flow
> * Generous whitespace
> * Strong alignment and grid structure
> * No unnecessary gradients
> * No decorative visual clutter
>
> Typography should resemble a premium modern SaaS website:
>
> * Large bold product headline
> * Clear medium-weight section titles
> * Short labels
> * Minimal body copy
> * No long paragraphs
>
> The overall visual language should feel like something created manually by a **product designer working with a software architect**.
>
> ---
>
> # HEADER
>
> Place the **product logo and product name** at the top left.
>
> Under it, add a small product category.
>
> Example:
>
> `SPOTIFY`
>
> `Music streaming & discovery`
>
> Then add a large product-focused headline.
>
> Example:
>
> **Discover the right music for every moment.**
>
> Underneath, add one concise supporting sentence.
>
> Example:
>
> `Search, stream and discover music personalized to your listening habits.`
>
> At the top-right, optionally display **2–3 meaningful metrics**.
>
> Example:
>
> `10M+ tracks`
> `50K playlists`
>
> Only use metrics supplied by the user. **Never invent statistics.**
>
> ---
>
> # MAIN IMAGE STRUCTURE
>
> Use approximately **three major visual sections**.
>
> ## 1. Sources / Inputs
>
> Show the important external inputs feeding the application.
>
> Use approximately **2–4 vertically stacked cards**.
>
> Each should contain:
>
> **Icon + short title + one short descriptor**
>
> Example:
>
> **Music catalog**
> `Tracks & albums`
>
> **Artist metadata**
> `Genres & releases`
>
> **Listening activity**
> `Plays & preferences`
>
> Keep descriptions extremely short.
>
> Connect these cards visually into the next stage.
>
> ---
>
> ## 2. Core Processing / Architecture
>
> Show only the **essential product pipeline**, normally 3–5 steps.
>
> Example:
>
> **1. Ingest**
> `Collect catalog data`
>
> ↓
>
> **2. Analyze**
> `Extract signals`
>
> ↓
>
> **3. Personalize**
> `Rank recommendations`
>
> ↓
>
> **4. Serve**
> `Deliver results`
>
> Do not expose unnecessary internal implementation detail.
>
> The viewer should understand the architecture conceptually without needing to read a technical document.
>
> For different product types, adapt the workflow appropriately.
>
> Examples:
>
> **AI research agent**
>
> `Prompt → Research → Reason → Generate`
>
> **Document intelligence**
>
> `Upload → Parse → Extract → Review`
>
> **E-commerce**
>
> `Catalog → Search → Recommend → Checkout`
>
> **Analytics platform**
>
> `Sources → Transform → Analyze → Dashboard`
>
> **Developer tool**
>
> `Code → Analyze → Build → Deploy`
>
> ---
>
> ## 3. Product Experience
>
> Make this the **largest section in the image**.
>
> Show a simplified version of the actual application inside an appropriate device or application frame.
>
> Examples:
>
> * Desktop browser for SaaS
> * Laptop for web applications
> * Phone for mobile-first products
> * Dashboard panel for internal tools
>
> For a Spotify-style product, the mockup could show:
>
> **Your Music**
>
> `Made for you`
>
> `[Album] Discover Weekly`
>
> `[Album] Daily Mix`
>
> `[Album] Release Radar`
>
> plus a simple bottom playback bar.
>
> The mockup should communicate the real product experience without reproducing the entire screenshot.
>
> ### Product mockup rules
>
> * Use realistic device proportions
> * Never stretch the laptop or screen
> * Preserve the application's general visual hierarchy
> * Increase important text for presentation readability
> * Remove tiny controls
> * Remove secondary navigation
> * Show only 1–3 important outputs
> * Avoid miniature screenshots containing unreadable text
> * Prefer simplified reconstructed UI over shrinking a full screenshot
>
> The viewer should immediately understand:
>
> **"What does this application actually give the user?"**
>
> Add a short action-oriented title above the product.
>
> Examples:
>
> **Discover. Play. Enjoy.**
>
> **Search. Compare. Decide.**
>
> **Research. Generate. Deliver.**
>
> **Upload. Analyze. Understand.**
>
> **Build. Test. Deploy.**
>
> Choose wording specific to the application.
>
> Do **not** add a separate features sidebar unless absolutely necessary. Show product capabilities through the interface itself.
>

>
> # TECH STACK BAR
>
> Place a clean horizontal **Tech stack** section across the bottom of the image.
>
> Group technologies logically.
>
> Example:
>
> **Frontend**
>
> React · TypeScript
>
> **Backend**
>
> Python · FastAPI
>
> **Data**
>
> PostgreSQL · Redis
>
> **AI**
>
> PyTorch
>
> **Infrastructure**
>
> Docker · AWS · GitHub
>
> Show recognizable technology logos with their names.
>
> Keep this section compact and visually consistent.
>
> Avoid unnecessary implementation labels such as:
>
> `repo-name`
>
> `main.py`
>
> `(comments)`
>
> `(snapshot)`
>
> `(finder.js)`
>
> `(optional)`
>
> unless they communicate something essential about the product.
>
> ---
>
> # CONTENT SIMPLIFICATION RULES
>
> Favor **short product language** over technically complete sentences.
>
> For example, convert:
>
> `The system records a user's listening history and uses embedding similarity to calculate personalized recommendations`
>
> into:
>
> **Personalize**
> `Rank music for each listener`
>
> Convert:
>
> `Metadata from multiple external music providers is normalized and inserted into the search index`
>
> into:
>
> **Ingest**
> `Collect catalog metadata`
>
> Convert:
>
> `Search requests are processed through several backend services and returned to the frontend`
>
> into:
>
> **Search**
> `Find tracks instantly`
>
> Think in terms of:
>
> **Verb + outcome**
>
> rather than implementation explanation.
>
> ---
>
> # INFORMATION HIERARCHY
>
> Prioritize information in this order:
>
> **Product value**
>
> ↓
>
> **Product experience**
>
> ↓
>
> **How it works**
>
> ↓
>
> **Tech stack**
>
> ↓
>
> **Implementation details**
>
> The architecture supports the product story—it should not dominate it.
>
> ---
>
> # AVOID
>
> Do not create:
>
> * Dense system architecture diagrams
> * Long paragraphs
> * Tiny text
> * Large blocks of technical explanation
> * More than approximately 4–5 processing stages
> * Redundant feature cards
> * Generic AI brain illustrations
> * Excessive gradients
> * Too many colors
> * Oversized icons
> * Fake metrics
> * Distorted laptops or phones
> * Full screenshots shrunk until unreadable
> * Repetition between headline, features and architecture
>
> ---
>
> # FINAL QUALITY TARGET
>
> The finished image should look appropriate for:
>
> **Developer portfolio · LinkedIn project showcase · Engineering case study · Product architecture deck**
>
> A viewer should understand within roughly **10 seconds**:
>
> **What it is → what it does → how it works → what it is built with.**
>
> Keep the final composition **minimal, technical, credible, product-focused and presentation-ready.**
>
> When the supplied application information is overly detailed, **simplify it rather than trying to display everything**.
>
> Preserve technical correctness, but prioritize visual communication and clarity.
